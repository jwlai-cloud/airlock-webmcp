01
The primitive

A page can hand an agent verbs

WebMCP is an imperative browser API at document.modelContext. A page registers tools: named, schema'd JavaScript functions an agent can discover and call.

What matters is what it replaces. An agent acting on a page previously had two options — drive the DOM (brittle, and it sees everything), or call a server API (needs a backend, auth, and a contract agreed in advance). WebMCP adds a third: the page declares what it is willing to have done to it, in its own words, and the browser mediates every call.

  1. Register — the page calls registerTool() with a name, description, JSON Schema, and an execute callback.
  2. Discover — the agent asks the browser for the currently active tools.
  3. Invoke — the agent requests a call with arguments matching the schema.
  4. Execute — the browser mediates, then runs execute inside the registering page's own context: its variables, its DOM, its already-authenticated session.
  5. Respond — the callback returns structured content to the agent.

Step four is the one Airlock is built on. The publisher's data never leaves the publisher's page, because the code that touches it runs there.

02
Reading the IDL

The description is prompt, not documentation

// the normative interface, W3C spec §4.2
[Exposed=Window, SecureContext]
interface ModelContext : EventTarget {
  Promise<undefined>                 registerTool(ModelContextTool tool, optional ModelContextRegisterToolOptions options = {});
  Promise<sequence<RegisteredTool>>  getTools(optional ModelContextGetToolOptions options = {});
  Promise<DOMString>                 executeTool(RegisteredTool tool, optional object inputObject = {}, optional ModelContextExecuteToolOptions options = {});
  attribute EventHandler ontoolchange;
};

dictionary ToolAnnotations {
  boolean readOnlyHint = false;
  boolean untrustedContentHint = false;
};

Read SecureContext literally: HTTPS or localhost, nothing else. That is why local development needs no certificates — http://localhost is a secure context by definition, so exposedTo: ["http://localhost:8787"] is accepted.

name, description and inputSchema are the entire basis on which a model decides whether to call your tool. They are prompt, not comments. Airlock's row-export tool is described as "Export user-level rows. This is never permitted and always refuses." — which tells the model the refusal is by design, so it reports it rather than retrying with different arguments.

The double parse — step through a real call step 0 / 3

The double parse is not a bug and not a workaround. The outer parse yields the MCP envelope; the inner parse yields whatever your tool serialised into that envelope's text slot.

Note what the broker gets back: not a denial. An empty list. It does not learn the tools exist, so it cannot probe them, and there is no error message to mine for structure. This is a capability, not an access-control check inside the tool.

04
The core move

A permission check can be argued with. A missing tool cannot.

The conventional way to gate a sensitive capability leaks:

// the usual approach — and why it fails
execute: async (input) => {
  if (!consentGranted) return { error: "consent required" };  // ← the tool still exists
  ...
}

The tool sits in the agent's list. Its name and description are in the model's context. Everything after that is a negotiation — one a confused user, or injected text asserting consent was already given, can win. The refusal message is itself an oracle: it confirms the capability is there.

Airlock does not register the tool at all:

// consent creates the capability
let overlapAbort = null;

function registerOverlap() {
  overlapAbort = new AbortController();
  document.modelContext.registerTool(
    { name: "estimate_overlap", /* ... */ },
    { signal: overlapAbort.signal }          // ← registration is bound to the signal
  );
}

// revocation is real removal, not a flag flip
overlapAbort.abort();

Press inject before granting consent. The injected text is perfectly persuasive and changes nothing, because persuasion operates on the model and the model is not what is holding the gate. Each transition fires a toolchange event, so an agent caching a stale list is told to refresh.

05
What actually crosses

Counts, above a floor — or nothing

Origin B holds 4,200 synthetic user rows. Three tools are the only way in, and none of them can emit a row: reach returns a count, overlap returns a count or a suppression, and export refuses unconditionally.

The suppression floor is k = 250: a returned count always describes at least 250 people, so no individual is identifiable from it. Drag the cohort below the floor and watch the number fail to cross.

k-anonymity, k = 250 released
Say the limit out loud. This is k-anonymity, not differential privacy. Repeated queries with varied cohort definitions can still narrow an individual down. Airlock states this in its README rather than waiting for a judge to find it — an honest limit costs less than an overclaim.
06
Hostile text

The hint is advisory, so don't rely on it

Free text arrives from the other origin — segment notes, written on the far side of a trust boundary, reaching both the model and origin A's DOM. The spec offers untrustedContentHint, and is candid about what it is: a signal permitting a client to sanitize, spotlight, or hide the payload. It sanitizes nothing on its own, and a client may ignore it.

So Airlock layers two defences, neither sufficient alone. Send the publisher's note through and watch both fire:

note attached to segment "sports-fans", authored on origin B

What defeats the injection is not cleverness about the text. Even a model that believes it entirely finds that publisher_export_rows refuses, and that estimate_overlap was never a row-returning tool. Layered, not clever.

The textContent rule is not cosmetic either. Rendering partner strings with innerHTML would hand origin B script execution inside origin A — the boundary would leak in the opposite direction from the one being advertised. Airlock's tools/check.sh fails the build if an HTML sink appears on either page.

07
Errata

Where Chrome 152 and the published spec disagree

Each of these costs about an hour to rediscover under time pressure.

ThingPublished / expectedChrome 152 reality
entry pointnavigator.modelContext in several write-ups document.modelContext
executeTool arg 1a tool name, in several write-ups the RegisteredTool object from getTools()
executeTool arg 2spec IDL says object inputObject must be a JSON string; an object throws UnknownError: Failed to parse input arguments
executeTool returnPromise<DOMString> matches — a JSON string, parse it
requestUserInteraction absent from the W3C IDL and from Chrome's own docs exists in Chrome's model_context.idl; its receiver is pinned down by no published spec

Note the third row precisely: the divergence is on input only. The spec always said the return is a DOMString.

The last row is why Airlock probes for requestUserInteraction on both plausible receivers and falls back to a direct dialog. An API that no published specification pins down should not be the single point of failure for a demo's central claim.
