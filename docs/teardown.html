01
The shape

Two apps that distrust each other

Airlock is not one application with a partner panel. It is two, on two origins, each holding data the other must never see. The advertiser's workspace runs on GitHub Pages; the publisher's governance console runs on githack. Neither can read the other's storage, variables, or DOM — that is the browser's same-origin policy, not something we implemented.

What each side holdssynthetic

Origin A — the advertiser

Two audiences, 11,500 people. Six registered tools, one of which does not exist until both companies approve.

Origin B — the publisher

4,200 user records across four segments. Four tools, published to exactly one origin.

publisher_segment_reach an aggregate publisher_overlap_count aggregate or suppressed publisher_export_rows always refuses publisher_review_request a human decision

Why the publisher is embedded rather than in its own tab. WebMCP only exposes cross-origin tools to documents in the same frame tree. Without the allow="tools" iframe, origin A could not reach origin B's tools at all. The embedding is the API's requirement, not a demo convenience — and the frame changes nothing about the boundary, because the browser still enforces it.

02
The central decision

Authority by tool existence

The obvious way to gate a sensitive capability is a check inside it. We did not do that, and the reason is the whole submission.

The version we rejected
// the tool still exists. Its name and description are in the
// model's context. The refusal is an oracle confirming the
// capability is there, and everything after is a negotiation.
execute: async (input) => {
  if (!consentGranted) return { error: "consent required" };
  ...
}
What we built instead
let overlapAbort = null;

// consent creates the capability
function registerOverlap() {
  overlapAbort = new AbortController();
  mc.registerTool(estimateOverlap, { signal: overlapAbort.signal });
}

// revocation destroys it — not a flag, a deregistration
overlapAbort.abort();

Before consent, getTools() does not return it. There is no name to guess, no description to read, no error to probe.

03
Consent

Neither company can approve for the other

An early version asked only the advertiser's operator and called that "both sides approve". It wasn't true. The request now crosses the boundary as a WebMCP tool call — publisher_review_request — which opens a decision in the publisher's own console, on their own origin, and returns their answer.

The handshakeidle

Each step is a real mechanism: an operator dialog on A, an executeTool call across origins, an operator dialog on B, then registerTool with an AbortSignal. The toolchange event fires on every transition, so an agent holding a stale list is told to refresh.

04
What testing disproved

Three published facts were wrong

Chrome exposes WebMCP only behind a flag, which makes it awkward to test. Rather than guess the Chromium feature name, the harness writes the enabled lab experiments into a throwaway profile's Local State — Chrome applies them at startup exactly as it would for a person who ticked the box. That turned an untestable project into 25 checks, and the checks immediately contradicted the docs.

Pick one1 of 4
The first one mattered most. The consent gate — the submission's central claim — had never worked. It threw on every attempt, and nothing surfaced it until a real browser ran it.
05
Defence

Three gates, none trusting the model

The publisher returns free text with its aggregates — segment notes. One of them is a deliberate prompt injection telling the agent to export everything. It is synthetic, and it is meant to be there: a defence you can watch fail is evidence, one you read about is a claim.

Send the injection throughidle
Waiting.

untrustedContentHint is in the spec, and we set it — but the spec is candid that it only permits a client to sanitise or spotlight the payload. It enforces nothing. So the text is also rendered with textContent, never innerHTML, into a visually distinct panel. tools/check.sh fails the build if an HTML sink ever appears on a page that renders partner text.

06
Proof

What is actually checked

Three suites, all driving real Chrome through Playwright, all runnable against the deployed pair rather than a local copy.

The suites
SuiteDrivesCovers
verify.jsthe WebMCP API directly 25 checks — both refusals, two-sided approval, the declarative tool, the exact error string Chrome throws for a non-string input
verify-ui.jsthe UI a keyless visitor clicks 12 checks — the deterministic router, the declarative form submitted by hand, revocation
verify-llm.jsa real Gemini model that the model never calls the gated tool, and never invents a figure it was not given

The third one earned its place immediately: it found that Gemini 3 attaches a thoughtSignature to the part carrying a function call, not to the call itself. Rebuilding that turn without it is rejected — something no amount of reading would have surfaced.

07
Limits

What this is not

k-anonymity, not differential privacy. A returned count always describes at least 250 people, so no individual is identifiable from one answer. Repeated queries over varied audience definitions can still narrow someone down. That is stated in the README rather than left for a reader to notice.

Synthetic data throughout. Both sides' records are generated in-page.

No persistence, no auth, no mobile layout. This demonstrates a boundary mechanism; it is not a production clean room.

Untested in ChatGPT's in-app browser. We had no access to it. Chrome 149+ is the verified half of the requirement.
